# Hermes Pipeline — Known Limitations & Notes

Документация ограничений обёртки Hermes-плагина относительно авторитетного Standalone.

> ⚠️ Это **не баг-репорты**, а информационные заметки для разработчика.
> Standalone — авторитетный референс; обёртка следует ему, но с отставанием.

---

## 1. Не реализовано в обёртке (отсутствует функциональность)

### compose режим
- `_safe_deep_research` всегда возвращает JSON-доказательство (compose=False)
- Markdown-композиция (compose.py) не вызывается
- **Последствие:** агент получает сырые данные, синтез делает сам (LLM)
- **Standalone:** compose=True возможен через `compose.py`

### image_search качество
- Обёртка: `image_search` возвращает `thumbnail` / `page_url` — не полноразрешенные изображения
- Standalone: page-HTML extraction (`extract_fullsize_images` + sieve) — настоящие fullsize-изображения из страниц
- **Последствие:** визуальные отчёты в Hermes хуже по качеству изображений

### gallery links секция
- Standalone: `_build_report` содержит `## Gallery Links` раздел для визуальных запросов
- Обёртка: нет такого раздела
- **Последствие:** для визуальных тем агент не видит удобных ссылок на галереи

### image filter (format/dedup/size)
- Standalone: `_filter_images_for_report` — Pillow-based фильтрация (формат, контент-хэш, размеры)
- Обёртка: нет фильтрации изображений
- **Последствие:** изображения могут быть низкого качества, дубликаты не удаляются

### LLM enrichment (person queries)
- Standalone: `enrich_query` — LLM находит алиасы/псевдонимы для персон
- Обёртка: нет enrichment
- **Последствие:** person-запросы могут возвращать менее полные результаты

## 2. Архитектурные различия

### _coverage модуль
- `_is_coverage_sufficient` в обёртке ловит исключение и возвращает False
- В Standalone `_coverage` может отменить Level-2 expansion если тема покрыта
- **Последствие:** Level-2 expansion запускается чаще (при alive < 15 всегда), может быть избыточно

### Schema enum
- Обёртка: `["visual", "technical", "news", "historical", "comparison", "video", "general"]`
- Standalone: те же + `person`, `fact`, `science`, `education`, `art` (в query_variants.py оркестратора)
- **Последствие:** некоторые типы запросов не имеют специализированных вариантов

## 3. Контекст-бюджет (текущие параметры)

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| `max_result_size_chars` для `web_deep_research` | `32000` | было 60000 |
| `max_result_size_chars` для `web_expand_and_fetch` | `16000` | было 40000 |
| `MAX_EVIDENCE_PAGES` | `18` | было final_limit=25 |
| `MAX_EVIDENCE_CHARS` | `28000` | ~18 страниц × 1500 компактированных символов |
| `_COMPACT_PER_PAGE` | `1500` | потолок текста страницы, который реально видит LLM |
| Порог релевантности | `0.15` / `0.05` (visual) | зеркалит standalone (порог 0.05 visual, 0.15 прочие) |
| Мин. длина текста | `300` / `50` (visual) | зеркалит standalone; визуальные страницы скупы на текст |
| Домен-квота | `6` с домена + Jaccard 0.85 | Jaccard — основной анти-дуп; квота лишь против доминирования одного источника |

**Обоснование:** 92K контекста − 20–25K инструкции Hermes ≈ 67K доступно. 32K результата + 25K инструкции = 57K < 67K. Запас ~10K для синтеза.

**Quality-first filtering:** перед итоговым отбором применяется relevance threshold (0.15 / 0.05 для visual) и минимальная длина текста (300 / 50 для visual) — отсекает SEO-мусор и поверхностные страницы. После этого evidence проходит Jaccard-дедуп + доменную квоту, сортируется по relevance и наполняется в budget до 28K chars / 18 страниц (бюджет считается по компактированному размеру, который реально видит LLM).

## 4. Domain diversity & source selection (controversial decisions)

### Domain quota: 6 per domain (max_per_source_url = 6)

**Почему не "1 с домена":**
- Reddit может содержать несколько уникальных обсуждений по одной теме — жёсткий лимит 1 теряет нюансы
- Документация/форумы/блоги — разные типы источников, каждый может дать разные углы зрения

**Почему не "без лимита":**
- Один домен может доминировать в контексте (например, 30 страниц с Reddit = 45K chars, переполнение)
- Множество похожих страниц от одного источника создают иллюзию "согласия" без реальной новой информации

**Компромисс:** 6 страниц с домена + Jaccard-дедупликация (threshold 0.85)
- Если страницы похожи (>85% пересечение токенов) — берём только одну
- Если страницы разные по сути — до 6 штук: несколько релевантных Reddit-тредов по теме выживают, но один источник не забивает контекст
- Jaccard — главный фильтр повторов (одинаковые ответы разных пользователей имеют высокое пересечение токенов); квота — вторичная защита от доминирования

### Relevance threshold: 0.15 (0.05 для visual)

**Почему не 0.0 (брать всё):**
- SEO-мусор, keyword-stuffing страницы могут иметь relevance 0.1-0.3 по инструментальным причинам (token overlap)
- Поверхностные статьи ("что такое X — 5 предложений") часто имеют высокий keyword-match но низкую ценность

**Почему не 0.5 (только отбор топ):**
- Для rare/specific тем релевантные страницы могут иметь relevance 0.2-0.4 (не много совпадений, но это единственные источники)
- Слишком жёсткий порог рискует оставить агента без данных

**Почему 0.05 для visual:** визуальные запросы нацелены на галереи/изображения — такие страницы могут иметь мало текстовых совпадений, но быть релевантными. Зеркалит standalone (img_threshold = 0.05 для visual).

**Компромисс:** 0.15 — это "есть хоть какая-то реальная тема" vs "случайный overlap". Combined with min_text_length — отсекает поверхностные страницы.

### Минимальная длина текста: 300 chars (50 для visual)

**Обоснование:**
- Страницы с <300 chars текста обычно: SEO-стubs, страницы с преимущественно изображениями без контекста, редиректы
- Для deep research нужен контент глубиной, а не одно предложение
- Для visual порог снижен до 50 — страницы-галереи скупы на текст, но ценны картинками (в обёртке картинки идут отдельно через image_search)

## 5. Key implementation decisions

### Evidence budget flow:

```
pages + expand_items (до 40+ items)
    ↓
Quality filter: relevance >= threshold (0.15 / 0.05 visual) AND text_length >= (300 / 50 visual)
    ↓
Post-retrieval filter: Jaccard dedup (0.85) + per-domain cap (6) → ≤ 18 pages
    ↓
Sort by relevance DESC
    ↓
Budget fill: until MAX_EVIDENCE_PAGES (18) OR MAX_EVIDENCE_CHARS (28000),
             measured on COMPACTED size (min(len(text), 1500) per page)
    ↓
Compact: _compact_evidence (1500 chars/page)
    ↓
Return: ≤18 pages × ~1500 chars ≈ ≤27K + panel + variants + images ≈ ≤32K
```

### Почему relevance-first sort + budget, а не просто final_limit:

- `final_limit=18` без sorting брал бы первые 18 страниц в порядке поступления (не гарантированно релевантные)
- Сортировка по relevance + budget filling гарантирует: лучшие страницы в пределах budget, остальные отсекаются
- Бюджет измеряется по компактированному размеру (1500/стр), а не по сырому тексту (до 5000) — иначе эффективный лимит составлял бы ~5 страниц, а не 18

### Проброс relevance (важно):

- Level-1: `relevance` приходит из бэкенда `search_deep` (`ddg_search._relevance_score`, 0–1) и кладётся в словарь страницы
- Level-2 (expand items): `relevance` вычисляется через `content_relevance_score(query, text)` — тот же скоринг, что в standalone
- Без этого поля quality-фильтр отсекал бы все страницы (значение по умолчанию 0)

### Известный trade-off: два разных скорера под одним порогом

Level-1 страницы скорится бэкендом `_relevance_score` (простое word-overlap: подстрока, без фразового гейта), а Level-2 — `content_relevance_score` (фразовый гейт + нормализация). Пороги 0.15/0.05 калибровались в standalone на `content_relevance_score`, поэтому:
- keyword-stuffed страница может получить высокий балл `_relevance_score` и пройти гейт
- релевантная Level-2 страница с редкими формулировками может не пройти фразовый гейт и быть отсечена

Практическое влияние низкое (порог 0.15 достаточно мягкий), но если в реальных прогонах появится систематический перекос — стоит считать `content_relevance_score` единообразно и для Level-1 (пересчёт на тексте страницы вместо `_relevance_score` бэкенда).
